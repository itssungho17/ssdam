# SSDAM

**Structured Skill-Driven Automation Mechanism**

A Human–AI collaborative development and operation mechanism that defines **Task** as the top-level execution unit, structures work through a validated pipeline, and enforces quality, traceability, and recoverability at every step.

> SSDAM operates on *"What has been validated"* — not *"What has been done."*

## What is SSDAM?

SSDAM is a framework for running software development projects where AI agents and humans share responsibility. It replaces informal, activity-based progress tracking with a pipeline of contractually connected, evidence-backed state transitions.

Every piece of work passes through the same five-element flow:

```
Execution → Artifact → Evaluation → Evidence → Checkpoint
```

Progress is granted only when a Checkpoint passes — not when an activity is finished, not when a file is created.

---

## Core Concepts

| Concept | Description |
|---------|-------------|
| **Mission** | A higher-level intent composed of multiple Tasks. Not directly executable. |
| **Task** | The atomic executable unit. Has explicit input/output contracts, produces verifiable Artifacts, and terminates via Checkpoint. |
| **Execution** | Activities performed within a Task to produce an Artifact. |
| **Artifact** | The reviewable output of an Execution step. |
| **Evaluation** | Verification applied to an Artifact against defined criteria. |
| **Evidence** | Objective justification that backs an Evaluation decision. |
| **Checkpoint** | The sole PASS / FAIL decision gate. No implicit transitions. |
| **Recovery** | Structured response when a Checkpoint fails. Must modify input, strategy, constraints, or skill selection — repeating the same execution is not allowed. |
| **Skill** | A reusable execution capability invoked by a Task. |

## Pipeline

SSDAM provides a two-phase pipeline of Agent Skills.

### Phase 1 — Spec Generation

| Skill | Trigger | Output |
|-------|---------|--------|
| `new-mission` | `/new-mission` | `mission-spec.yaml` — full mission definition with tasks, requirements, governance |
| `new-task` | `/new-task <mission-spec-path> <TSK-NNN>` | `task-spec.TSK-NNN.yaml` — fully specified task with contracts, evaluation criteria, and execution plan |

### Phase 2 — Execution Skills

Each `task-spec` execution plan contains steps that map 1-to-1 to these skills. Run them in order.

```
architecture-design (mandatory)
       │
       ├── data-modeling
       │       └── schema-design
       │
       ├── backend-design ──── backend-implementation
       │
       └── frontend-design ─── frontend-implementation
```

| Skill | Trigger | Output |
|-------|---------|--------|
| `architecture-design` | `/architecture-design <task-spec-path>` | `architecture-design.TSK-NNN.md` — module boundaries, component diagram, API contract overview, domain entities |
| `data-modeling` | `/data-modeling <task-spec-path>` | `data-modeling.TSK-NNN.md` — entity definitions, Mermaid ERD, relationships, indexes |
| `schema-design` | `/schema-design <task-spec-path>` | `schema-design.TSK-NNN.sql` — DDL for all tables |
| `backend-design` | `/backend-design <task-spec-path>` | `backend-design.TSK-NNN.md` — API endpoints, service/repo layer, error handling, test strategy |
| `backend-implementation` | `/backend-implementation <task-spec-path>` | Code in `project_root/` (autonomous agent execution) |
| `frontend-design` | `/frontend-design <task-spec-path>` | `frontend-design.TSK-NNN.md` — pages, component tree, state management, API integration |
| `frontend-implementation` | `/frontend-implementation <task-spec-path>` | Code in `project_root/` (autonomous agent execution) |

> `backend-implementation` and `frontend-design` can run in parallel once `backend-design` is complete.

## Runtime Output Structure

When the pipeline runs, it writes all output to a workspace folder under `.ssdam/`:

```
.ssdam/
└── {workspace-id}/
    ├── input/
    │   └── mission-input.yaml       ← auto-generated by new-mission
    └── output/
        ├── mission-spec.yaml        ← generated by new-mission
        ├── task-spec.TSK-001.yaml   ← generated by new-task
        ├── task-spec.TSK-002.yaml
        └── design/
            ├── architecture-design.TSK-001.md
            ├── data-modeling.TSK-001.md
            ├── schema-design.TSK-001.sql
            ├── backend-design.TSK-001.md
            └── frontend-design.TSK-001.md
```

## Getting Started

For a full step-by-step walkthrough — including Cursor setup, `package.json` configuration, skill status, and the correction loop — see the **[Quickstart Guide](./en/01_overview/quickstart.md)**.

### Quick overview

| Step | Command |
|------|---------|
| 1. Install skills | Copy `templetes/` → `.cursor/skills/` |
| 2. Configure | Edit `.cursor/skills/new-mission/assets/package.json` |
| 3. Create mission | `/new-mission <idea or feature list>` |
| 4. Create task spec | `/new-task @mission-spec.yaml TSK-001` |
| 5. Run execution skills | `/{exec_type} @task-spec.TSK-001.yaml EXEC-01` → ... |

## Design Principles

1. **Task is the top-level execution unit** — Tasks are atomic; Missions are containers.
2. **Contract-driven design** — Every Task has explicit input and output contracts.
3. **Artifact-driven progress** — Progress requires validated Artifacts, not completed activities.
4. **Evidence-based decisions** — No PASS or FAIL without supporting Evidence.
5. **Checkpoint authority** — The only way to advance or recover is through a Checkpoint.
6. **Failure is a designed event** — Failures are classified, preserved, and recovered through a defined strategy.
7. **End-to-end traceability** — Requirement → Task → Artifact → Evaluation → Checkpoint.
8. **Human / Agent responsibility model** — Agents execute; humans own accountability.
