# 🛠 Stage Design Guide — 스테이지 설계 가이드

## 1. 개요

이 문서는 SSDAM 스테이지를 **처음부터 설계하는 실무 절차**를 정의한다.

01_principles의 불변 규칙과 02_architecture의 구조를 전제로 하며,
07_reference의 각 요소 정의를 실제 설계 행위로 연결한다.

설계 절차:

```
목적 정의 → 계약 설계 → 평가 기준 수립 → 체크포인트 정책 → Recovery 전략 → 설계 검증
```

---

## 2. Step 1 — 목적 정의

스테이지 설계는 **단일 목적(Purpose)**을 정의하는 것에서 시작한다.

### 2.1 작성 항목

| 항목 | 설명 | 예시 |
|------|------|------|
| 목적 | 이 스테이지가 달성하려는 것 | "엔티티 간 관계를 구조화한다" |
| 범위 | 목적의 경계 | "논리적 모델만 다룬다. 물리적 최적화는 범위 밖" |
| 완료 기준 | 목적 달성을 판단하는 기준 | "모든 엔티티의 관계가 ERD로 표현된다" |

### 2.2 검증 질문

- 이 스테이지의 목적을 한 문장으로 설명할 수 있는가?
- 목적이 두 가지 이상의 관심사를 포함하고 있지 않은가?
- 완료 기준이 검증 가능한 형태인가?

### 2.3 안티패턴

- ❌ "백엔드 전체 구현" → 다중 목적, 분리 필요
- ❌ "코드 작성 및 테스트" → 두 관심사 혼합
- ✅ "API 엔드포인트 구현" → 단일 목적

---

## 3. Step 2 — 계약 설계

목적이 정의되면 **입력 계약과 출력 계약**을 설계한다.

### 3.1 입력 계약

이 스테이지가 시작되기 위해 필요한 것:

| 항목 | 설명 |
|------|------|
| 선행 Artifact | 어떤 산출물이 필요한가 |
| 형식 | 어떤 포맷/구조여야 하는가 |
| 품질 조건 | 선행 Artifact의 최소 품질 기준 |
| 추가 입력 | 요구사항, 정책, 제약 조건 등 |

예시:

```
입력 계약:
  - requirements.md (PRD, Checkpoint PASS 완료)
  - constraints.md (기술 제약 조건)
```

### 3.2 출력 계약

이 스테이지가 생성해야 하는 것:

| 항목 | 설명 |
|------|------|
| Artifact 목록 | 생성할 산출물 |
| 형식 | 각 Artifact의 포맷/구조 |
| 품질 기준 | 후행 스테이지가 요구하는 최소 품질 |
| 메타데이터 | 버전, 작성자, 시점 등 |

예시:

```
출력 계약:
  - schema.mmd (Mermaid ERD, 모든 엔티티 포함)
  - data-dictionary.md (필드 정의, 타입, 제약조건)
```

### 3.3 계약 설계 원칙

- 후행 스테이지가 사용하지 않는 출력을 강제하지 않는다 (인터페이스 분리)
- 구체 구현이 아닌 형식/구조에 의존한다 (의존성 역전)
- 입력은 해당 스테이지가 실제로 필요한 항목만 포함한다

---

## 4. Step 3 — 평가 기준 수립

Artifact가 생성된 후 **어떤 기준으로 평가할 것인지**를 사전에 정의한다.

### 4.1 평가 유형 선택

| 유형 | 적용 상황 | 예시 |
|------|----------|------|
| 계약 검증 | 입출력 형식 준수 확인 | 스키마 Validation |
| 품질 검증 | 정확성/완전성/일관성 확인 | 테스트 커버리지 ≥ 80% |
| 정책 검증 | 조직 규칙/보안/규제 준수 | 보안 스캔 통과 |
| 휴먼 리뷰 | 맥락 기반 판단 필요 시 | 아키텍처 결정 리뷰 |
| 에이전트 평가 | 자동화/반복 검증 적합 시 | 정적 분석 실행 |

하나의 스테이지에 **복수 유형을 조합**할 수 있다.

### 4.2 품질 임계값 설정

각 평가 기준에 대해 PASS/FAIL 경계를 정량적으로 정의한다.

예시:

| 기준 | 임계값 | 측정 방식 |
|------|--------|----------|
| 테스트 통과율 | ≥ 95% | 자동 테스트 리포트 |
| 커버리지 | ≥ 80% | Coverage 도구 |
| 응답 지연 | ≤ 200ms (P95) | 성능 벤치마크 |
| 보안 취약점 | Critical 0건 | 보안 스캐너 |

### 4.3 정성 평가 기준

정량화가 어려운 항목은 판단 기준을 명문화한다.

예시:

```
아키텍처 리뷰 기준:
  - 요구사항과의 정합성이 설명 가능한가
  - 확장 시나리오에 대한 대응이 식별 가능한가
  - 기술 부채 리스크가 문서화되어 있는가
```

### 4.4 검증 질문

- 모든 평가 기준이 PASS/FAIL로 판정 가능한가?
- 기준이 모호하거나 측정 불가능한 항목은 없는가?
- Evidence로 뒷받침할 수 있는 구조인가?

---

## 5. Step 4 — 체크포인트 정책 선택

Evaluation 결과를 바탕으로 **누가, 어떻게 PASS/FAIL을 판정할 것인지**를 결정한다.

### 5.1 게이트 유형 선택

| 유형 | 적용 상황 |
|------|----------|
| 자동 정책 게이트 | 정량 기준이 명확하고 자동 측정 가능 |
| 사람 승인 게이트 | 고위험 판단, 전략적 결정, 맥락 기반 평가 |
| 하이브리드 게이트 | 자동 평가 결과 + 사람 최종 승인 |

### 5.2 선택 기준

```
정량 기준만으로 판정 가능? → 자동 정책 게이트
맥락/전략 판단 필요?        → 사람 승인 게이트
자동 평가 + 사람 확인 필요? → 하이브리드 게이트
```

### 5.3 정책 명세 작성

체크포인트 정책은 다음을 포함해야 한다:

- PASS 조건 (모든 조건 충족 필요)
- FAIL 조건 (하나 이상 해당 시)
- 판정 주체 (Policy / Human / Agent)
- 기록 항목 (판정 결과, 시각, 근거 링크)

---

## 6. Step 5 — Recovery 전략 사전 정의

**실패가 발생하기 전에** 대응 전략을 설계한다.

### 6.1 예상 실패 유형 식별

스테이지 특성에 따라 발생 가능한 실패를 나열한다.

| 실패 유형 | 예시 |
|----------|------|
| Validation Failure | 테스트 미통과 |
| Contract Violation | 출력 형식 불일치 |
| Missing Evidence | 리뷰 기록 누락 |
| Quality Failure | 커버리지 미달 |
| Logical Failure | 설계 모순 발견 |
| Dependency Failure | 외부 API 장애 |

### 6.2 실패별 Recovery 전략 매핑

| 실패 유형 | Recovery 전략 | 자동/수동 |
|----------|--------------|----------|
| Validation Failure | Artifact 수정 후 재평가 | 자동 가능 |
| Contract Violation | 계약 정합성 복구 | 수동 권장 |
| Missing Evidence | 근거 보강 | 자동/수동 |
| Quality Failure | 리팩토링 후 재실행 | 자동 가능 |
| Logical Failure | 구조 재설계 (Re-stage) | 수동 필수 |
| Dependency Failure | 대체 경로 / 재시도 | 자동 가능 |

### 6.3 에스컬레이션 조건

다음 조건을 사전에 정의한다:

- 최대 Recovery 시도 횟수 (예: 3회)
- 동일 실패 반복 시 사람 개입 기준
- 불확실성 임계값 초과 시 승격 기준

## 7. Step 6 — 설계 검증

설계가 완료되면 다음 체크리스트로 최종 검증한다.

### 7.1 SSDAM 호환성 체크리스트

**목적**

- [ ] 단일 목적이 명확히 정의되어 있다
- [ ] 목적을 한 문장으로 설명할 수 있다
- [ ] 완료 기준이 검증 가능하다

**계약**

- [ ] 입력 계약이 명시되어 있다
- [ ] 출력 계약이 명시되어 있다
- [ ] 불필요한 입출력이 포함되어 있지 않다
- [ ] 구체 구현이 아닌 형식/구조에 의존한다

**평가**

- [ ] 평가 유형이 선택되어 있다
- [ ] 품질 임계값이 정량적으로 정의되어 있다
- [ ] 모든 기준이 PASS/FAIL 판정 가능하다
- [ ] Evidence로 뒷받침 가능한 구조이다

**체크포인트**

- [ ] 게이트 유형이 선택되어 있다
- [ ] PASS/FAIL 조건이 명시되어 있다
- [ ] 판정 주체가 정의되어 있다

**Recovery**

- [ ] 예상 실패 유형이 나열되어 있다
- [ ] 실패별 Recovery 전략이 매핑되어 있다
- [ ] 에스컬레이션 조건이 정의되어 있다

**SOLID**

- [ ] 단일 책임 — 하나의 목적만 가진다
- [ ] 개방/폐쇄 — 구조 변경 없이 확장 가능하다
- [ ] 리스코프 치환 — 동일 계약의 다른 스테이지로 교체 가능하다
- [ ] 인터페이스 분리 — 입출력이 최소 단위로 분리되어 있다
- [ ] 의존성 역전 — 구현이 아닌 계약에 의존한다

## 9. 실전 예시

### Stage: 엔티티 관계도 (ERD)

**목적:**
요구사항에서 도출된 엔티티 간 관계를 구조화한다.

**범위:**
- 포함: 논리적 엔티티 관계 모델링
- 제외: 물리적 최적화, 인덱스 설계

**입력 계약:**

| Artifact | 형식 | 출처 |
|----------|------|------|
| requirements.md | Markdown | 요구사항 정의 Stage |
| constraints.md | Markdown | 아키텍처 스케치 Stage |

**출력 계약:**

| Artifact | 형식 | 용도 |
|----------|------|------|
| schema.mmd | Mermaid ERD | 데이터 설계 기반 |
| data-dictionary.md | Markdown | 필드 정의 참조 |

**평가 기준:**

| 유형 | 기준 | 임계값 | 측정 방식 |
|------|------|--------|----------|
| 계약 검증 | 모든 엔티티가 ERD에 포함 | 100% | 요구사항 대비 체크 |
| 품질 검증 | 네이밍 규칙 준수 | 100% | 정적 검증 |
| 휴먼 리뷰 | 관계 정합성 | 리뷰 승인 | 설계 리뷰 |

**체크포인트 정책:**
- 게이트 유형: 하이브리드 (자동 검증 + 사람 리뷰)
- PASS 조건: 계약 검증 PASS + 품질 검증 PASS + 리뷰 승인
- FAIL 조건: 위 조건 중 하나라도 미충족
- 판정 주체: 자동 정책 + 설계 리뷰어

**Recovery 전략:**

| 예상 실패 | 전략 | 자동/수동 |
|----------|------|----------|
| 엔티티 누락 | ERD 보완 후 재평가 | 자동 가능 |
| 관계 오류 | 설계 수정 후 재리뷰 | 수동 |
| 네이밍 위반 | 자동 수정 후 재검증 | 자동 |

**에스컬레이션:**
- 최대 Recovery 횟수: 3
- 리뷰 2회 연속 FAIL 시 아키텍트 개입

## ✅ 핵심 요약

스테이지 설계는:

> **"작업을 나열하는 것"이 아니라
> "목적·계약·평가·회복을 사전에 구조화하는 행위"**

설계 시점에 정의되지 않은 것은 실행 시점에 혼란이 된다.
SSDAM에서 좋은 스테이지는 실행 전에 이미 검증 가능한 구조를 갖춘 스테이지이다.
