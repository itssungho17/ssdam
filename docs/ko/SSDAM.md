# SSDAM (SOLID 스테이지 기반 자동화 메커니즘)

SSDAM은 **Stage를 최상위 단위로 정의하고**,
각 Stage가 **SOLID 원칙을 따르도록 설계된 실행 구조** 위에서
**실행 → 산출물 → 평가 → 근거 → 체크포인트**
흐름을 통해 산출물과 근거를 구조화·검증하여
품질, 추적성, 회복력을 동시에 확보하는
**개발·설계·AI 협업 운영 시스템**이다.

---

## 🎯 1. 목표

SSDAM의 목표:

- SOLID 원칙 기반 스테이지 설계 정착
- 산출물 중심 개발 체계 확립
- 검증 가능한 의사결정 구조 확보
- 실패를 통제 가능한 이벤트로 전환
- 에이전트 기반 개발의 신뢰성 강화

---

## 🧱 2. 핵심 모델

SSDAM은 다음 실행 모델로 작동한다:
```
Start → Stage 1 → Stage 2 → ... → Stage N → END
```
각 스테이지는 다음과 같은 흐름을 따른다:
```
실행(Execution) → 산출물(Artifact) → 평가(Evaluation) → 근거(Evidence) → 체크포인트(Checkpoint) → 다음 스테이지 / 회복(Recovery)
```

---

| 요소 | 설명 |
|------|------|
| **스테이지** | **SOLID 원칙을 적용해 설계된 최상위 목적 단위** |
| **실행** | 스테이지 내 수행 활동 |
| **산출물** | 실행의 검토 가능한 결과물 |
| **평가** | 산출물에 대한 검증/판단 과정 |
| **근거** | 평가 결과를 정당화하는 근거 |
| **체크포인트** | 통과 / 실패 판정 지점 |
| **다음 스테이지** | 체크포인트 통과 시 진행 대상 |
| **회복** | 체크포인트 실패 시 수행할 회복 활동 |

---

## 🧩 3. 스테이지 설계 원칙 (SOLID)

SSDAM에서 모든 스테이지는 다음 **SOLID 원칙**을 따른다:

| 원칙 | 스테이지 적용 의미 |
|------|----------------|
| **S — 단일 책임 원칙** | 스테이지는 하나의 명확한 목적만 가진다 |
| **O — 개방/폐쇄 원칙** | 스테이지 구조는 안정적으로 유지되며 변경은 어렵고 확장은 가능해야 한다 |
| **L — 리스코프 치환 원칙** | 스테이지 변형/세분화에도 입력/출력 계약이 유지되어야 한다 |
| **I — 인터페이스 분리 원칙** | 스테이지 입력/출력 계약은 최소 단위로 분리된다 |
| **D — 의존성 역전 원칙** | 스테이지는 구체 구현이 아닌 요소별 계약에 의존한다 |

---

## 🚦 4. 스테이지

스테이지는 작업 단위가 아니라 **목적 단위**이다.
각 스테이지는 명확한 목표와 종료 기준을 가지며,
검증 가능한 산출물을 생성해야 한다.

### ✅ 스테이지 정의 조건

- 단일 목적을 가진다
- 명확한 입력 / 출력 계약을 정의한다
- 검증 가능한 산출물을 생성한다
- 평가 수행 가능 구조를 가진다
- 근거 기반 판단이 가능하다
- 체크포인트 종료 기준이 존재한다

---

### 📥 스테이지 입력

- 선행 스테이지의 산출물
- 관련 근거
- 정의된 계약(요구사항 / 명세 등)

---

### 📤 스테이지 출력

- 검토 가능한 산출물
- 평가 결과
- 생성된 근거

---

### 🔄 스테이지 종료

스테이지는 **체크포인트 평가**를 통해 종료된다.

- **통과** → 다음 스테이지 진행
- **실패** → 실패 기록 + 회복 수행

---

### 🧱 예시 스테이지

- 아이디어 정의
- 제품 요구사항 문서
- 아키텍처 스케치
- 엔티티 관계도
- 데이터 정의 언어
- 백엔드 슬라이스
- 프론트엔드 슬라이스
- 테스트 및 검증
- 배포 계획
- 배포 후 검토

---

## 🔁 5. 실패 처리 철학

SSDAM에서 실패는 예외가 아니라:

> **통제 가능한 상태 전이 이벤트**

실패는 다음 조건 중 하나 이상 충족 시 선언된다:

- 평가 기준 미충족
- 산출물 계약 위반
- 필수 근거 누락
- 품질 임계값 미달
- 위험 수준 허용치 초과

실패 시 수행 절차:

1. 실패 분류
2. 근거 보존
3. 회복 전략 선택
4. 재실행 / 재평가 / 재스테이지

---

## 🔗 6. 추적성 원칙

SSDAM은 모든 의사결정을 다음 체인으로 연결한다:

```
요구사항
→ 스테이지
→ 실행
→ 산출물
→ 평가
→ 근거
→ 체크포인트
```

변경 발생 시 추적 체인은 보존되며,
수정 이력은 단절 없이 유지되어야 한다.

효과:

- 의사결정 역추적 가능
- 감사 / 검토 대응 가능
- AI 판단 정당화 가능
- 실패 원인 분석 가능

---

## 🤖 7. 에이전트 호환성

SSDAM은 사람 / AI 에이전트 공존을 전제로 설계된다.

| 역할 | 가능한 수행자 |
|------|----------------|
| 실행 | 사람 / 에이전트 |
| 평가 | 사람 / 에이전트 |
| 체크포인트 | 정책 / 사람 |
| 회복 | 사람 / 에이전트 |

에이전트는 역할 수행이 가능하나,
최종 책임은 스테이지 소유자에게 귀속된다.

사람은 언제든 에이전트 판단을 재정의할 수 있으며,
고위험 실패 또는 불확실성 증가 시 사람에게 에스컬레이션이 발생한다.

에이전트 기반 평가 결과는
신뢰도 / 불확실성 메타데이터를 포함해야 한다.

체크포인트 유형:

- 자동 정책 게이트
- 사람 승인 게이트
- 하이브리드 게이트

---

## 📐 8. 설계 목표

SSDAM은 다음 특성을 지향한다:

- **결정적 흐름**
- **산출물 기반 진행**
- **근거 기반 의사결정**
- **명시적 실패 통제**
- **조합 가능한 스테이지 아키텍처**
- **추적 가능한 의사결정**
- **회복 가능한 실패**

각 설계 목표는 SSDAM의 불변 조건으로 간주된다.

설계 목표를 위반하는 확장 또는 변형은
SSDAM 호환으로 간주되지 않는다.

결정적 흐름은
상태 전이 규칙과 체크포인트 판정 기준의 결정성을 의미한다.

## ✅ 10. 요약

SSDAM은:

> **"작업 관리 시스템"이 아니라
> "품질·검증·근거 중심 실행 메커니즘"이다.**

SSDAM에서 진행은 활동이 아니라
**검증 가능한 상태 전이**로 정의된다.

- **스테이지**는 진행 단위이며
- **산출물**은 진척 단위이며
- **근거**는 신뢰 단위이다.

완료는 산출물의 존재가 아니라
**체크포인트 통과**로 선언된다.

실패는 예외가 아니라
**통제 가능한 시스템 이벤트**이며,
회복은 보정이 아니라
**설계된 회복 전략의 실행**이다.

SSDAM은 다음을 보장하도록 설계된다:

- 임의적 진행 방지
- 근거 없는 의사결정 차단
- 실패의 구조적 관리
- 변경의 추적 가능성
- 사람 / 에이전트 협업 안정성

결과적으로 SSDAM은:

> **"무엇을 했는가"보다
> "무엇이 검증되었는가"를 중심으로 작동하는 시스템이다.**
